# KaizenSpeech — отчёт о найденных ошибках и рисках

Проверено: 1892 карточки в `phrases.txt`, `repetitions.json` (382 КБ), 100 % тестов проходят (`pytest Tests -q`). Уже задокументированные в проекте проблемы (Issue 2, 3, 9, 10, 16, 21, 22, 46) помечены отдельно — они ниже не раскрываются, кроме случаев, когда их последствия шире, чем описано.

## 1. Критично: потеря и порча пользовательских данных

### 1.1. Нечитаемый `repetitions.json` молча заменяется пустой структурой и перезаписывается на диске — вся история обучения теряется
`system_level.py:84-94` возвращает `{}` при **любом** исключении, `flywheel.py:19` принимает это как «карточек нет», `data_level.py:52-59` пересоздаёт все карточки с нулевой историей, `flywheel.py:30/49/59` записывает результат поверх исходного файла.

Проверено: файл с одной битой записью (`repetition_number: 9`, `time_to_repeat: "2030.13.45"`) → вывод `Cannot open or parse repetitions.json file: JSONDecodeError(...)` → `Added 1892 new phrases` → `Session finished. All data saved.`, exit code 0. История (EF, streak, attempts, даты) уничтожена без резервной копии и без вопроса к пользователю.

Так же ведёт себя `user_statistics.txt` (`flywheel.py:22`, `60`): `attempts_num: 500` → `{}`.

Это поведение закреплено тестом как ожидаемое: `Tests/test_system_level.py:160-162` — «A corrupted repetitions.json must not stop the session: it is replaced by an empty structure».

### 1.2. Частичное чтение `phrases.txt` приводит к массовому удалению карточек
`system_level.py:33-59`: `try` охватывает **весь цикл**, `except Exception` возвращает уже разобранный частичный словарь. `data_level.py:67-70` трактует отсутствующие в нём фразы как удалённые пользователем и стирает соответствующие карточки.

Проверено: один недопустимый байт в строке 401 из 601 → разобрано 227 фраз → `Removed 373 phrases` → история 373 карточек уничтожена, exit code 0, сообщение «All data saved».

Защита `data_level.py:42-46` срабатывает только при **полностью** пустом словаре, то есть когда файл небольшой и ошибка чтения случилась в пределах первого буфера (~8 КБ). Для реального `phrases.txt` (72 КБ) защита не действует. Тестов на частичное чтение нет.

### 1.3. BOM в `phrases.txt` создаёт дубль первой карточки и удаляет оригинальную
`system_level.py:34` использует `encoding='utf-8'`, а не `utf-8-sig`.

Проверено: тот же файл, сохранённый в UTF-8 with BOM (штатный сценарий для Notepad/PowerShell `Out-File`), → ключ первой строки становится `'\ufeffWhat is it?'` → `Added 1 new phrases, Removed 1 phrases`: новая пустая карточка вместо карточки с историей.

### 1.4. Одна битая запись в `repetitions.json` убивает сессию (за пределами Issue 9)
Issue 9 описывает `ValueError` в `determine_next_phrase` (`data_level.py:95-98`). Проверены и другие точки:
- `data_level.py:62` — `KeyError: 'translations'` в `merge()`, если у записи нет этого поля;
- `data_level.py:62` — `TypeError: 'int' object is not subscriptable`, если значение записи не словарь;
- `data_level.py:164` — `AttributeError` при `translations: null`, `TypeError` при вложенном списке (`[['hola']]`) или нестроковом элементе.

Ни один из этих путей не перехватывается: сессия падает с трейсбеком после того, как `merge()` уже мог изменить данные в памяти.

### 1.5. `user_statistics.txt` вообще не валидируется
`data_level.py:24-35` проверяет только `phrases` и `repetitions`; `flywheel.py:22` загружает статистику без проверки.

Проверено: `user_statistics.txt` с содержимым `[]` или `"abc"` → сессия стартует нормально, первый же ответ → `TypeError` с трейсбеком. Строковое значение под ключом `native_words` (`"abc"`) молча превращается в список символов `['a','b','c', ...]` (`data_level.py:127-128`).

## 2. Критично: падения процесса

### 2.1. `UnicodeEncodeError` при любом перенаправленном выводе — и потеря только что данного ответа
Приложение не переопределяет кодировку stdout; тесты обходят это через `PYTHONIOENCODING` (`Tests/test_flywheel.py:40-41`, Issue 46), но в самом приложении проблемы нет.

Проверено (`python flywheel.py > log.txt`, cp1251, без `PYTHONIOENCODING`): exit code 1, `UnicodeEncodeError: 'charmap' codec can't encode character '\xe9' in position 5`. Падение происходит внутри `_print_colored_diff` (`ui_level.py:44-55`) — **до** `dop.update_repetitions` (`flywheel.py:44`) и до сохранения, то есть введённый пользователем ответ теряется, а сессия обрывается трейсбеком.

Затронуты все символы, отсутствующие в cp1251: `é`, `ñ`, `í`, `ó`, `ú`, `¿`, `¡`. В `phrases.txt` 903 варианта содержат такие символы.

### 2.2. `EOFError` не обрабатывается
`ui_level.py:15` — `input()` без перехвата; `flywheel.py:54` ловит только `KeyboardInterrupt`.

Проверено: закрытый stdin при активном файле → exit code 1, `EOFError: EOF when reading a line`, трейсбек, нет ни «Session finished», ни финального сохранения (`flywheel.py:59-60` недостижимы).

### 2.3. `find_or_create_file` падает без обработки при создании файла
`system_level.py:24` — `open(filename, 'w')` вне `try`. Проверено: read-only/недоступный CWD → `PermissionError` с трейсбеком вместо сообщения об ошибке.

### 2.4. Скрытый `KeyError` в основном цикле
`flywheel.py:39` — `repetitions[current_phrase]` без проверки; `determine_next_phrase` возвращает `''` при пустом словаре (`data_level.py:104`). Недостижимо при текущем порядке вызовов (гард `data_level.py:32`), но не защищено ни кодом, ни тестом.

## 3. Логические ошибки (без падения, но с неверным результатом)

### 3.1. Порог `level_good` не согласован с метрикой Jaro: «Not bad» = провал по SM-2
`data_level.py:17-19` против `data_level.py:251` (`>= level_good` считается успехом).

Проверено на реальном `phrases.txt`:
- **747 карточек из 1892 (39,5 %)**: грамматически верный ответ, набранный **без ударений**, оценивается ниже 0.97 → UI печатает «Not bad», а SM-2 фиксирует провал (сброс `repetition_number`, падение EF). Примеры: `'Y que?'` против `'Y qué?'` → 0.8667; `'Yo no se'` против `'Yo no sé'` → 0.9167; `'Para que?'` → 0.9167; `'Lo esta'` против `'Lo está'` → 0.9048 (при этом «правильным ответом» пользователю показывается `'Lo es'` — другой вариант).
- Нормализации Unicode (NFD/снятие диакритики) в `_compact` (`data_level.py:187-196`) нет: `é.isalnum()` истинно, поэтому ударение считается полноценным расхождением. `'si'` против `'sí'` → 0.6667.
- Одна случайная опечатка в реальной фразе: медиана 0.9667, **57 %** ответов попадают в «Not bad» → провал по SM-2; `'te qiero'` против `'te quiero'` → 0.9630 → провал.

В реальных данных пользователя это уже отразилось: обе отвеченные карточки имеют `repetition_number: 1`, `easiness_factor: 1.8` — результат пары ответов, оценённых как провал.

### 3.2. Интервал SM-2 не является рекуррентным
`data_level.py:256-258`: `6 * easiness_factor` вместо `I(n-1) * EF`. Комментарий `data_level.py:57` утверждает, что интервал растёт.

Проверено (EF ≈ 2.5–2.8): интервалы `1 → 6 → 16 → 16 → 17 → 17` дней и дальше не растут. Поведение закреплено тестом `Tests/test_data_level_supermemo.py:30-34` (rep=5, EF=2.0 → ровно 12 дней).

### 3.3. `determine_next_phrase` сравнивает с `now` вместо сравнения двух кандидатов
`data_level.py:103`: `if min_time_to_repeat_started_phrases <= datetime.now() or recommended_continuing_phrase == ''`.

Проверено:
- начатая карточка, становящаяся доступной через 1 час, проигрывает новой карточке со сроком через 5 дней — самая ранняя по сроку карточка пропускается;
- обратный случай: если все карточки начаты и ни одна не просрочена, возвращается карточка с **будущей** датой — повторение происходит раньше срока, что ломает интервальное повторение.

Существующий тест `Tests/test_data_level_determine_next_phrase.py:32-38` использует 2 дня против 1 дня и этот случай не покрывает.

Дополнительно: имя `recommended_continuing_phrase` (`data_level.py:94`, `100-101`) присвоено переменной, хранящей **ни разу не начатую** карточку, а `recommended_started_phrase` — начатую; семантика имён инвертирована относительно содержимого.

### 3.4. `SequenceMatcher` без отключения autojunk портит подсветку длинных фраз
`data_level.py:215`: `isjunk` задан, но `autojunk` не отключён — для строк ≥ 200 символов difflib объявляет «популярные» символы мусором.

Проверено: эталон 200 символов, почти верный ответ → **100 символов помечены красным**; 300 символов → 150 красных. `max_phrase_len` поднят до 300 (Issue 28), то есть диапазон полностью рабочий; тесты проверяют только оценку похожести (`test_data_level_similarity.py:73-86`), но не подсветку.

### 3.5. `_print_colored_diff` молча теряет символы
`ui_level.py:51-55`: у `if i - 1 >= 0 and i + 1 < len(reference)` нет `else`. Проверено: эталон `' ab'` с картой `[False, True, True]` печатает `'ab'` — символ исчез из «правильного ответа». Функция не покрыта тестами вообще.

### 3.6. Карта ошибок строится от `lower()`, а печатается оригинал
`data_level.py:200-201`: `reference = reference.lower()`, затем `correction_map = [True] * len(reference)`. `ui_level.py:21` передаёт в печать исходный `best_translation`.

Проверено: для символов, меняющих длину при `lower()` (U+0130 `İ`), длина карты 9 → 10, индексы разъезжаются, подсветка смещается относительно эталона.

### 3.7. Правило `n >= 3` делает короткие фразы полностью красными
`data_level.py:220`. Проверено: `find_user_mistakes('sí', 'sí')` → `[False, False, True]`; `('si', 'sí')` → `[False, False]`. Для эталона из 2–3 символов ни один блок совпадений не достигает длины 3, поэтому даже идеальный ответ отображается как полностью неверный.

### 3.8. Обрезка ввода выполняется до очистки
`data_level.py:239-241`: `user_input[:max_phrase_len]` применяется к сырому вводу, до удаления запрещённых символов и `strip()`. Проверено: ответ ровно в 300 символов плюс один лишний символ теряет последний **значимый** символ, а не мусор.

### 3.9. Ограничение `attempts` срабатывает только «точно в размер»
`data_level.py:112`: `if len(...) == max_attempts_len`. Если в файле уже больше 10 записей (ручное редактирование, миграция), список не возвращается к пределу и растёт неограниченно.

### 3.10. Пустой ввод принимается как ответ и оценивается в 0.0
`ui_level.py:15-21` не проверяет пустую строку; `find_max_string_similarity('', ...)` возвращает `(0.0, translations[0])` (`data_level.py:172-185`). Проверено: нажатие Enter → «Wrong» → провал по SM-2 (сброс streak, EF −0.8), запись в `attempts`, рост `attempts_num`. Команды «пропустить карточку» в приложении нет (только `/exit`).

### 3.11. `sys.exit()` без кода при фатальных ошибках → статус 0
`data_level.py:26`, `data_level.py:30`, `flywheel.py:73`. Проверено: «Cannot parse repetitions file» и «Both structures have zero length» завершают процесс с кодом **0** — внешне успешный запуск. При этом `flywheel.py:70` корректно использует `sys.exit(1)`.

### 3.12. «No new phrases» маскирует ошибку загрузки
`data_level.py:40-46`: одно и то же сообщение возвращается и при штатном отсутствии изменений, и при срабатывании гарда пустого словаря. Проверено: `phrases.txt` не загрузился (0 фраз) при 1892 существующих карточках → `data_assessment` даёт `can_work=True` (`data_level.py:32` — условие «и», а не «или») → печать «No new phrases» → сессия идёт на устаревших переводах без предупреждения.

### 3.13. `read_json_from_file` сообщает об ошибке для штатного пустого файла
`system_level.py:88-93`. Проверено: первый запуск с пустыми `repetitions.json` / `user_statistics.txt` (созданы самим `find_or_create_file`) печатает `Cannot open or parse repetitions.json file: JSONDecodeError('Expecting value: line 1 column 1 (char 0)')`. Тесты `Tests/test_flywheel.py:32-33` специально создают пустые файлы и полагаются на проглатывание этой ошибки.

### 3.14. `find_or_create_file`: каталог считается файлом, поиск уходит за пределы проекта
`system_level.py:13-26`:
- `os.path.exists` (строка 15) истинно для каталога. Проверено: `find_or_create_file('Tests')` → `'Tests'`. Закреплено тестом `Tests/test_system_level.py:257-261` как ожидаемое поведение.
- `Path(__file__).parents[2]` (строка 19) = `C:\Work\github-pinned-repos` — обход **всех соседних репозиториев** в произвольном порядке `os.walk`; возвращается первое найденное совпадение, то есть данные чужого проекта могут быть прочитаны и перезаписаны (Issue 22 описывает факт обхода, но не риск записи чужих данных).
- Возвращаемый путь несогласован: относительный (строки 16, 26) или абсолютный (строка 21).

### 3.15. `save_json_to_file` превращает Ctrl+C в «сбой сохранения»
`system_level.py:127-132` ловит `KeyboardInterrupt`. Проверено: Ctrl+C во время сохранения → `Cannot save ...: KeyboardInterrupt()` → `flywheel.py:49-52` ставит `save_failed` → финальная печать «WAS NOT saved» и `sys.exit(1)` (`flywheel.py:70`) для штатного выхода.

### 3.16. Атомарность неполная
`system_level.py:117` — `fsync` только временного файла, каталог не синхронизируется; после `os.replace` (строка 123) при потере питания на POSIX возможна потеря самого переименования, несмотря на формулировку docstring (строки 98-103).

### 3.17. Финальное сохранение выполняется безусловно
`flywheel.py:59-60` вне зависимости от `save_failed` и от того, был ли хотя бы один ответ; при уже установленном `save_failed` сообщения об ошибке дублируются, а загруженная как `{}` статистика перезаписывает файл пользователя (см. 1.1).

### 3.18. Разбор `phrases.txt`: дубликаты и разделяемые объекты
`system_level.py:52-55`:
- один и тот же объект списка `english_part` присваивается нескольким ключам (алиасинг): последующая мутация затронет все связанные карточки;
- повторяющийся ключ в левой части молча перезаписывает предыдущий без предупреждения (в текущем `phrases.txt` таких строк 0 — дефект латентный).

### 3.19. Некорректные диагностические сообщения
- `system_level.py:40`: `String contains 3 "||" separators` для строки `a || b || c` — разделителей два, печатается число частей.
- `system_level.py:36`: `string[0]` — строка, состоящая только из `\n`, даёт `string[0] == '\n'` (проходит), а `UnicodeDecodeError` выводит в консоль **весь остаток файла** внутри `repr(e)` (проверено: тысячи символов мусора).
- Отступ перед `#` не распознаётся как комментарий (Issue 16), а `string[0]` без `strip()` — его причина.

## 4. Вывод и UX

### 4.1. ANSI-коды пишутся всегда, включая не-TTY
`ui_level.py:24-37`, `46-55` — никаких проверок `isatty()`. Проверено: в файле лога остаются `\x1b[39m`, `\x1b[32m` на каждый символ эталона (посимвольная раскраска даёт ~10 escape-последовательностей на короткую фразу).

### 4.2. `just_fix_windows_console()` вызывается на импорте модуля
`ui_level.py:8` — побочный эффект при импорте; любой импортирующий `ui_level` (включая тесты) меняет состояние консоли процесса.

### 4.3. Дублирование пустых строк
`ui_level.py:15`, `24`, `28`, `32`, `35` печатают `os.linesep` через `print()`, который сам добавляет перевод строки (Issue 10). Проверено в перехваченном выводе: `\r\n\r\n`.

### 4.4. Язык зашит в строку запроса
`ui_level.py:15` — `'in Spanish'` при том, что целевой язык нигде в данных не задаётся; `phrases.txt` может содержать любой язык.

## 5. Именование, данные, архитектура

### 5.1. Языки перепутаны местами во всём проекте
Формат `phrases.txt`: `английская фраза || испанский перевод`, но:
- `system_level.py:44-45` называет первую часть `'native'`, вторую — `'English'`;
- предупреждение `Warning. Too long English phrase variant` (`system_level.py:76`) печатается про **испанскую** фразу;
- `data_level.py:133-143` пишет слова испанского ответа в ключ `english_words`, а слова английского вопроса — в `native_words`.

Проверено на реальном `user_statistics.txt`: `"native_words": ["is","it","what"]` (английские), `"english_words": ["es","lo","que"]` (испанские). Закреплено тестом `Tests/test_data_level_determine_next_phrase.py:66-67`.

### 5.2. Файл с JSON называется `.txt`
`flywheel.py:11` — `user_statistics.txt` содержит JSON (`json.dump(..., indent=2)`).

### 5.3. Инверсия зависимостей уровней
`system_level.py:8` — «системный» уровень импортирует `max_phrase_len` из «уровня данных»; заявленная схема flywheel → ui → data/system нарушена (system зависит от data).

### 5.4. Каталог приложения — пакет с плоскими импортами
Пустой `Code/__init__.py` при абсолютных импортах `from data_level import ...`. Проверено: `python -m Code.flywheel` и `import Code.flywheel` из родительского каталога → `ModuleNotFoundError: No module named 'data_level'`.

### 5.5. `find_max_string_similarity` возвращает `max_distance`, являющийся похожестью
`data_level.py:158-185` — переменная и семантика имени противоположны содержимому (Jaro **similarity**); в `ui_level.py:20` она же называется `distance`.

### 5.6. Дефекты самих данных `phrases.txt`
- строка 12: `No Io sé` — заглавная `I` вместо строчной `l`; этот вариант сохраняется как эталон и может быть показан пользователю как «правильный ответ»;
- 69 строк содержат одновременно варианты с ударением и без (`Lo es | Lo está`, `No se | No lo se | Yo no sé`): результат оценки одного и того же верного ответа зависит от того, какой вариант совпал лучше;
- непоследовательная пунктуация: часть вопросов хранится без `¿` и без ударений (`Que es?`), часть — с ними (`Y qué?`).

### 5.7. Дублирование кода
`data_level.py:120-131` и `133-143` — два почти идентичных 10-строчных блока; `data_level.py:149-152` дублирует сортировку, уже выполненную в `130-131`/`141-142`.
