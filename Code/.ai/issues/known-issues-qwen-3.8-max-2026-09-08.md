- Дата анализа: 08.09.2026
- Окружение: Python 3.12.7, jellyfish 1.2.1, colorama 0.4.6, pytest 9.1.1, Windows
- Состояние тестов на момент анализа: **58 passed, 6 xfailed** (`pytest Tests`, перезапущено после анализа)
- Все пункты ниже подтверждены эмпирически (запуск кода / замеры), а не только чтением исходников.
  Числовые значения (интервалы SM-2, сходство Jaro, счётчики ошибок, размеры файлов, число фраз)
  получены прогоном верификационного скрипта по реальным `phrases.txt` (1899 строк, 1892 ключа)
  и `repetitions.json` (1892 записи, 372 КБ)

## Соглашения

- Идентификаторы известных багов сохранены из ревью, на которое ссылается `Tests/test_known_issues.py`
  (Issue 2, 3, 9, 10, 16, 21). Новые дефекты пронумерованы от 22 вверх, чтобы номера не конфликтовали.
- Issue 6 (невалидная аннотация `-> (float, str)`) уже исправлена — см. `Tests/test_data_level_similarity.py`.
- Severity: `critical` (потеря данных / падение), `high` (некорректная работа основного сценария),
  `medium`, `low` (косметика, документация, гигиена).

## P0. Потеря данных пользователя

### Issue 22 — `find_or_create_file` ищет файлы не в проекте, а во всех репозиториях
- **Severity:** critical
- **Расположение:** `Code/system_level.py:8` (сигнатура, `parents_level_up: int = 2`), `Code/system_level.py:14` (`os.walk`)
- **Суть:** `Path(__file__).parents[2]` для `Code/system_level.py` даёт `C:\Work\github-pinned-repos`,
  т.е. каталог со **всеми** соседними репозиториями, а не корень проекта (`parents[1]` = `KaizenSpeech`).
- **Доказательство:** замер `Path(system_level.__file__).parents` →
  `0: ...\KaizenSpeech\Code`, `1: ...\KaizenSpeech`, `2: ...\github-pinned-repos`.
  Под этим корнем 6 репозиториев / 68 каталогов и **два** кандидата на имя `phrases.txt`:
  `KaizenSpeech\Code\phrases.txt` (72 КБ, испанский) и `KaizenSpeech\ru\phrases.txt` (162 КБ, русский).
  (`repetitions.json` в дереве один, поэтому файл прогресса берётся верно, а вот словарь фраз — нет.)
- **Влияние:** `os.walk` возвращает первое совпадение, порядок обхода зависит от файловой системы.
  При запуске не из `Code` может быть подхвачен русский файл (или файл чужого репозитория).
  Дальше `merge()` удалит из `repetitions` все фразы, которых нет в подхваченном файле, добавит новые
  и `flywheel` сразу это сохранит → **тихое уничтожение истории обучения**.
- **Фикс:** `parents_level_up=1` по умолчанию; детерминированный поиск (сначала каталог модуля, затем
  отсортированный обход); при нескольких кандидатах — предупреждение и выбор ближайшего к модулю;
  опционально — явный параметр пути или переменная окружения.

### Issue 23 — повреждённый JSON молча считается пустым словарём
- **Severity:** critical
- **Расположение:** `Code/system_level.py:68-78` (`read_json_from_file`), `Code/data_level.py:21-34`
  (`data_assessment`), `Code/flywheel.py:19-29`
- **Суть:** `except Exception` возвращает `{}` и для отсутствующего файла, и для пустого, и для обрезанного
  JSON. `data_assessment` обнаружить это не может — ошибка уже проглочена, а `phrases` непустой → `can_work = True`.
- **Доказательство:** `read_json_from_file` на обрезанном файле (`{"a": 1, `) и на несуществующем файле
  возвращает один и тот же результат `{}` (проверено); различаются только печатаемые сообщения
  (`JSONDecodeError(...)` и `FileNotFoundError(...)`), которые вызывающий код не видит.
- **Влияние:** после порчи `repetitions.json` (см. Issue 24) `merge()` пересоздаёт все 1892 фразы как новые
  (`attempts: []`, `time_to_repeat = now`, `easiness_factor = 2.5`), и `flywheel.py:29/42` перезаписывает файл.
  История теряется без единого вопроса пользователю.
- **Фикс:** различать три состояния (нет файла / пустой / ошибка разбора) — например, возвращать
  `(data, status)` или бросать отдельное исключение; при ошибке разбора делать резервную копию
  (`repetitions.json.corrupt-<timestamp>`) и аварийно выходить, не перезаписывая данные.

### Issue 25 — создаваемый файл не является валидным JSON
- **Severity:** medium
- **Расположение:** `Code/system_level.py:19-21`, `Code/flywheel.py:14-16,22`
- **Суть:** при первом запуске создаются пустые `repetitions.json` и `user_statistics.txt`. Пустой файл —

- **Влияние:** шум на старте, который приучает игнорировать сообщения об ошибках и маскирует реальную порчу

  «файл отсутствует / пустой» сообщение об ошибке не печатать.

## P1. Некорректная работа алгоритма интервальных повторений

### Issue 3 — SM-2 не переносит срок повторения после неправильного ответа
- **Severity:** high · **Статус:** известен, есть xfail-тест `Tests/test_known_issues.py::test_failed_answer_reschedules_repetition`
- **Расположение:** `Code/data_level.py:258-259`
- **Суть:** в ветке провала сбрасывается только `repetition_number`; `time_to_repeat` сохраняет прежнее
  (возможно, далёкое будущее) значение. По SM-2 после провала карта должна вернуться почти сразу (I(1) = 1 день).
- **Доказательство:** `_supermemo2(rep(time_to_repeat = now + 300 days), user_result = 0.0)` →
  `time_to_repeat` остаётся `now + 300 days`.
- **Влияние:** забытая фраза не возвращается в ближайшее время — основной учебный цикл не работает.
- **Фикс:** при `user_result < level_good` устанавливать `time_to_repeat = now` (или `now + короткий интервал`),
  сохранив сброс `repetition_number`.

### Issue 26 — интервал не растёт геометрически (отклонение от SM-2)
- **Severity:** high · **Статус:** новый, тестами не покрыт
- **Расположение:** `Code/data_level.py:254-256`
- **Суть:** для любого `repetition_number >= 2` интервал всегда равен `6 * easiness_factor` дней.
  В SM-2 используется рекуррентность `I(n) = I(n-1) * EF` (I(1)=1, I(2)=6, I(3)=6*EF, I(4)=6*EF² и т.д.).
- **Доказательство** (замер серии из 6 правильных ответов, `user_result = 1.0`):

  | n (repetition_number) | EF | интервал, дней |
  |---|---|---|
  | 1 | 2.6 | 1.0 |
  | 2 | 2.7 | 6.0 |
  | 3 | 2.8 | 16.2 |
  | 4 | 2.9 | 16.8 |
  | 5 | 3.0 | 17.4 |
  | 6 | 3.1 | 18.0 |

  Ожидалось по SM-2: 1 → 6 → 16.2 → 45.4 → 127 → 355.
- **Влияние:** интервал фактически упирается в ~2-3 недели и растёт лишь на `6 * 0.1 = 0.6` дня за ответ.
  Долгосрочное планирование (смысл интервального повторения) отсутствует: карточки не уходят на месяцы и годы.
- **Фикс:** хранить предыдущий интервал в записи (например, поле `interval_days`) и умножать его на EF;
  либо вычислять интервал как `6 * EF ** (repetition_number - 2)`. Добавить тест на рост интервала при n ≥ 3.

### Issue 27 — пороги оценки в UI и в алгоритме не согласованы
- **Severity:** high · **Статус:** новый
- **Расположение:** `Code/ui_level.py:23-35`, `Code/data_level.py:16-18,249,261-263`
- **Суть:** UI показывает «Not bad» при `level_mediocre (0.65) <= distance < level_good (0.97)`,
  но `_supermemo2` считает **любой** результат ниже 0.97 полным провалом и обнуляет `repetition_number`.
  При этом `easiness_factor` для такого ответа продолжает **расти** (формула EF применяется безусловно).
- **Доказательство** (Jaro-сходство типичных ответов после `_compact`):
  `'te kiero' / 'te quiero' = 0.8843`; `'hola' / 'ola' = 0.9167`; `'Lo se' / 'Yo se' = 0.8667`;
  `'No lo se' / 'No se' = 0.875`; `'Mucho gusto' / 'Mucho gustos' = 0.9722`.
  Для 0.8843: `5 - 5*0.8843 = 0.5785` → `EF += 0.1 - 0.5785*(0.08 + 0.5785*0.02) = +0.047`.
- **Влияние:** одна опечатка в короткой фразе = полный провал карточки (обнуление серии) при ободряющем
  сообщении «Not bad» и одновременном росте EF. Прогресс пользователя обесценивается, обратная связь
  противоречива. В связке с Issue 3 фраза при этом даже не переносится на ближайшее время.
- **Фикс:** согласовать шкалы — например, считать успехом `distance >= level_mediocre` с градацией качества
  (или ввести промежуточную оценку), а EF увеличивать только при реальном успехе; решение о порогах
  требует подтверждения владельца проекта.

### Issue 28 — обрезка ввода до 200 символов делает длинную фразу неотвечаемой
- **Severity:** high · **Статус:** новый, латентный (на текущих данных не проявляется)
- **Расположение:** `Code/data_level.py:233` (`max_string_size: int = 200`), `Code/data_level.py:237`
- **Суть:** `_cleanup_user_input` обрезает ввод пользователя до 200 символов, тогда как эталонная фраза
  не ограничена. Для фразы длиннее 200 символов пользователь физически не может дать полный ответ.
- **Доказательство** (эталон длиной 224 символа, собранный конкатенацией вариантов из `phrases.txt`;
  ввод — тот же эталон без изменений):
  `find_max_string_similarity(ref224, [ref224]) = 0.9633` — это ниже `level_excellent (0.99)` **и** ниже
  `level_good (0.97)`, т.е. идеальный ответ попадает в ветку «Not bad» и засчитывается SM-2 как провал.
  Длина ввода после `_cleanup_user_input`: 200 символов (из 224).
- **Текущие данные:** максимальная длина варианта фразы в `phrases.txt` — 27 символов (строка 1136);
  самая длинная строка файла (1356) содержит 343 символа, но она разбивается разделителем `|`
  на 15 коротких вариантов, поэтому сегодня баг не воспроизводится. Формат файла длину никак не
  ограничивает — пользователь может добавить длинную фразу и получить неудаляемый «вечный провал».
- **Фикс:** убрать/существенно поднять лимит (или обрезать эталон симметрично), предупреждать при загрузке
  `phrases.txt` о фразах длиннее лимита, добавить тест на длинную фразу.

### Issue 29 — `SequenceMatcher` без `autojunk=False` ломает подсветку ошибок
- **Severity:** high · **Статус:** новый, латентный
- **Расположение:** `Code/data_level.py:214`
- **Суть:** `SequenceMatcher(isjunk, a, b)` по умолчанию использует эвристику `autojunk=True`:
  при `len(b) >= 200` символы, встречающиеся в `b` чаще 1%, объявляются «мусором» и исключаются из совпадений.
- **Доказательство:** для эталона длиной 233 символа и **идентичного** ввода `find_user_mistakes`
  возвращает 35 позиций, помеченных как ошибки (ожидалось 0).
- **Влияние:** у длинных фраз подсветка ошибок показывает произвольные «ошибки» при полностью правильном ответе.
- **Фикс:** `SequenceMatcher(lambda ch: ..., user_input, minified_reference, autojunk=False)` + регрессионный тест.

## P2. Падения (необработанные исключения)

### Issue 30 — `EOFError` не обрабатывается
- **Severity:** critical · **Статус:** новый
- **Расположение:** `Code/ui_level.py:15` (`input(...)`), `Code/flywheel.py:47` (`except KeyboardInterrupt`)
- **Суть:** `input()` бросает `EOFError`, когда stdin закрыт или исчерпан (перенаправленный ввод, пайп,
  часть терминалов, запуск из планировщика). Ловится только `KeyboardInterrupt`.
- **Доказательство:** вызов `uop.user_session(...)` при исчерпанном stdin завершается traceback и кодом 1 —
  исключение выходит из `user_session` необработанным.
- **Влияние:** аварийное завершение без блока `flywheel.py:51-52`, т.е. **без финального сохранения**;
  пользователь видит traceback вместо корректного выхода.
- **Фикс:** перехватывать `EOFError` вместе с `KeyboardInterrupt` (в `user_session` возвращать `None, ''`
  либо в `flywheel` — `except (KeyboardInterrupt, EOFError)`), добавить тест.

### Issue 31 — `KeyError` при пустой выборке фразы и при неполной записи
- **Severity:** high · **Статус:** новый
- **Расположение:** `Code/data_level.py:82-105` (`determine_next_phrase`), `Code/data_level.py:61`
  (`merge`, обращение к `['translations']`), `Code/data_level.py:91` (`value['attempts']`), `Code/flywheel.py:36`
- **Суть и доказательства:**
  - `determine_next_phrase({})` возвращает `''` (проверено) → `flywheel.py:36` делает `repetitions['']`
    → `KeyError: ''`. Контракт функции допускает возврат пустой строки, вызывающий код к этому не готов.
  - Запись без ключа `attempts` → `KeyError: 'attempts'` внутри `determine_next_phrase`.
  - Запись без ключа `translations` → `KeyError: 'translations'` внутри `merge` (проверено:
    `merge({'hello': 'hola'}, {'hello': {'attempts': []}})` → `KeyError: 'translations'`), т.е. падение
    ещё до начала сессии.
- **Влияние:** приложение падает на старте или в цикле при неполном/повреждённом `repetitions.json`
  (например, после частичной записи — Issue 24).
- **Фикс:** валидировать структуру записи при загрузке/слиянии (набор обязательных полей + значения по
  умолчанию), пропускать и логировать некорректные записи; в `determine_next_phrase` не возвращать `''`,
  а сигнализировать «нет доступных фраз», и обработать этот случай в `flywheel.py`.

### Issue 9 — `ValueError` на повреждённой дате в `time_to_repeat`
- **Severity:** high · **Статус:** известен, есть xfail-тест `Tests/test_known_issues.py::test_corrupted_record_does_not_crash_next_phrase_selection`
- **Расположение:** `Code/data_level.py:92,97`
- **Суть:** `datetime.strptime(value['time_to_repeat'], datetime_format)` бросает `ValueError`, если строка
  даты повреждена (например, `'not-a-date'` после ручной правки файла или обрезанной записи).
